## 1. Global conventions

### 1.1 Base, versioning, content
- All new business endpoints live under `/api/v1`. `GET/POST /api/auth/*` (NextAuth, already exists) is out of scope for versioning.
- Request/response bodies are JSON (`application/json; charset=utf-8`), except document downloads (redirects, §3.7) and generated audit-export files retrieved from private storage through §3.9 (format `TBD-TECH-04`).
- Unknown/extra request fields MUST be rejected with `422` (strict DTOs) to prevent silent contract drift.
- Breaking changes require `/api/v2`; additive optional fields are non-breaking.

### 1.2 Authentication & sessions
- Authentication is the existing NextAuth session cookie (HttpOnly, `__Secure-` in production, SameSite=Lax — already configured in the baseline). API endpoints MUST NOT accept credentials in URLs or custom headers for browser flows.
- Every `/api/v1` handler MUST authenticate the session server-side (except explicitly public endpoints) and MUST authorize by role **and** resource ownership (§6). UI hiding is never authorization.
- Sessions MUST be revocable (account disable, password change, explicit revoke). Mechanism (database sessions vs JWT + token-version) is `TBD-TECH-01`; the *behavior* in this contract is mandatory.
- Mutating cookie-authenticated requests MUST be CSRF-protected (NextAuth mechanisms and/or same-origin verification) — `TBD-TECH-02`.

### 1.3 Roles (proposed — final matrix is `TBD-PO-03`)
| Code | Role | Notes |
|---|---|---|
| `OWN` | Owner | Full access incl. user administration |
| `OPS` | Operations Manager | Operational modules; internal quotation approval (boundary TBD-PO-03) |
| `CRD` | Coordinator | Customers, requests, first contact, scheduling, invitations |
| `INS` | Inspection Engineer | Assigned inspections and results |
| `PM` | Project Manager | Own projects: milestones, diary, progress, reports, documents, handover |
| `QA` | Quality Engineer | Findings/quality within assigned projects (final-close authority TBD-PO-03) |
| `CUST` | Customer (portal) | Own records only, server-scoped (§6 SEC-01) |
| `STAFF` | Any of OWN/OPS/CRD/INS/PM/QA | Shorthand used below |

Endpoint **Auth** fields use these codes as **provisional role sets only**. They are not the company's approved permission policy. A staff role match is never sufficient by itself where §3.11 requires an assignment, parent-resource, separation-of-duties, or sensitive-authority predicate. Until `TBD-PO-03` approves those predicates, the affected endpoints are contract-blocked and implementations MUST deny the action rather than treating `STAFF` as blanket access. `CUST` is not a staff role and never satisfies `STAFF`.

### 1.4 Identifiers & references
- `id`: opaque server-generated string, immutable, never sequential-guessable in URLs (exact format is the colleague’s choice, `TBD-DB-04`).
- `reference`: human-facing code (e.g. request number shown to customers/staff), unique per entity type, generated via the `ReferenceSequence` port (§5.3). Exact format is `TBD-PO-11`.
- Clients MUST NOT infer ownership, ordering, or existence from IDs/references.

### 1.5 Data formats
- Timestamps: ISO 8601 UTC (`2026-10-24T10:30:00Z`). Calendar dates: `YYYY-MM-DD`. Server is the only clock authority for `createdAt/updatedAt`, `recordedAt`, and status-*recording* timestamps. A field explicitly defined as a reported event time (for example a progress `measuredAt`, reported customer-decision time, or reported contract `signedAt`) may be client-supplied under its DTO rules and is stored separately from the server recording time/actor.
- Money: integer **minor units** + explicit `currency` (ISO 4217). The current UI formats EGP (`src/lib/format.ts`), but the company’s currency/tax policy is `TBD-PO-04`; the API never uses floats for money.
- Phone numbers: stored and returned in E.164. Input normalization MUST match current UI behavior (Arabic-Indic/Persian digit folding, whitespace/`()-` stripping — see Appendix A). Default country for local-format numbers is `TBD-PO-10`.
- Localized text that is genuinely bilingual content (e.g. project titles today) uses `{ "ar": "...", "en": "..." }` to match the existing `LocalizedText` type. User-generated free text is a single string as typed.
- Percentages: numbers `0–100` (integers unless a DTO says otherwise), clamped/validated server-side.
- Enums are stable, entity-specific string keys. Keys already in `src/content/app-dictionary.ts` are display vocabulary, not a universal lifecycle. In particular, request `approved` retains its current workflow meaning (customer approved the proposal), while the quotation API in §2.5/§4.2 exposes separate internal-review, delivery, and customer-decision fields and MUST NOT use one overloaded quotation `status: "approved"`. Priorities remain `normal|high|urgent`. Entity-specific state machines in §4 define each value set; storage representation is `TBD-DB-04`.

### 1.6 Pagination, sorting, filtering, search (all list endpoints)
- Query: `page` (default 1), `pageSize` (default 20, max 100), `sort` (allow-listed per endpoint; an endpoint-specific default in §3 overrides the global default `createdAt desc`), `search` (optional), plus endpoint-specific filters. Invalid values → `400 INVALID_QUERY` (never silently ignored).
- Response: `Page<T>` = `{ items: T[], total: number, page: number, pageSize: number }`.
- Ordering MUST be deterministic (secondary stable key, e.g. `id`) so contract tests can assert page stability. Text-search semantics (case/diacritic folding for Arabic) are `TBD-DB-04` but MUST be documented by the adapter and covered by contract tests.

### 1.7 Error model
All errors: `{ "error": { "code": string, "messageKey": string, "fieldErrors"?: { [field]: string[] }, "details"?: object } }`.
`messageKey` is a stable localization key; the UI renders Arabic/English text — the API never returns user-facing prose. Internal details (SQL, stack traces, provider payloads) MUST NOT appear in responses.

| code | HTTP | Meaning |
|---|---|---|
| `MALFORMED_BODY` | 400 | Unparseable JSON / wrong content type |
| `INVALID_QUERY` | 400 | Bad pagination/sort/filter value |
| `UNAUTHENTICATED` | 401 | No/invalid/expired session |
| `FORBIDDEN` | 403 | Authenticated but role not allowed (staff surfaces) |
| `NOT_FOUND` | 404 | Does not exist — **or exists but is not owned by the calling customer** (portal) |
| `CONFLICT_STATE` | 409 | Illegal status transition or state precondition failed (e.g. editing a sent quotation) |
| `CONFLICT_VERSION` | 409 | Stale `version` (optimistic concurrency) |
| `IDEMPOTENCY_KEY_REQUIRED` | 400 | A POST that requires `Idempotency-Key` omitted it or sent an invalid key format |
| `IDEMPOTENCY_PAYLOAD_MISMATCH` | 409 | Same scoped idempotency key was reused with a different canonical payload hash |
| `IDEMPOTENCY_IN_PROGRESS` | 409 | Same scoped request is already being processed; includes `Retry-After`; no duplicate effect was executed |
| `EXPORT_NOT_READY` | 409 | Audit export exists but is not `ready` for a download grant |
| `EXPORT_EXPIRED` | 410 | Audit export file/grant window has expired; create a new export |

| `DEPENDENCY_UNAVAILABLE` | 503 | A required downstream (e.g. storage signing) is unavailable; business write was **not** half-applied |
| `INTERNAL` | 500 | Unexpected; logged with correlation id returned as `details.correlationId` |

Common set references below: **CE-AUTH** = 401/403/500 · **CE-STD** = CE-AUTH + 400/404/422 · **CE-LIST** = 401/403/400/500. Unknown input fields return `422 VALIDATION_FAILED` with `fieldErrors[field]: ["unknownField"]`; server-owned/read-only fields return `["readOnly"]`. They are never silently ignored.

### 1.8 Idempotency & concurrency
- **Where required:** `Idempotency-Key` is REQUIRED on every POST that creates a resource, export, upload/download grant, or outbox intent, or that performs a state action. It is OPTIONAL on PATCH because a required expected `version` already prevents stale writes; when supplied on PATCH, the same replay rules apply. Exceptions are password-reset/change and invitation acceptance (single-use secrets/current-password verification are their replay guards) and provider webhooks (provider event/message IDs are the replay guard). Missing/invalid required keys return `400 IDEMPOTENCY_KEY_REQUIRED` with no write. Keys are opaque 16–128 printable ASCII characters; clients SHOULD use UUIDv4 and MUST generate a new key for a new user intent, never derive one from PII or a record reference.
- **Uniqueness scope:** the uniqueness tuple is `(actorScope, HTTP method, route template, Idempotency-Key)`. `actorScope` is the authenticated staff `userId`, the authenticated portal `userId + customerId` from the session, or the reserved `public` partition for anonymous intake. The route template is the pattern (for example `/api/v1/portal/quotations/{id}/decision`), while concrete path values are included in the payload hash below. Therefore the same key used by another user/customer or on another endpoint is a different idempotency record and can never return the first caller's receipt.
- **Payload hash:** the server computes a collision-resistant hash (algorithm `TBD-TECH-03`; SHA-256 proposed) over a canonical representation of method + route template + concrete path parameters + effect-relevant query + the validated/normalized DTO. JSON member order and insignificant whitespace do not change the hash. The store retains the hash, never the raw body or PII. Same scoped key + different hash → `409 IDEMPOTENCY_PAYLOAD_MISMATCH` and no effect.
- **Concurrent and completed duplicates:** the server atomically claims a scoped key in `in_progress` state before any business side effect. A concurrent duplicate MUST NOT execute; it receives `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After`. After the business transaction commits, a replay returns the stored HTTP status and a safe response snapshot/resource reference without a second business write, audit entry, or outbox row. Auth, validation, and rate-limit failures do not consume a key. If the first attempt rolls back or fails before commit with a retryable dependency/internal error, the claim is released or marked retryable so the same intent may be retried. One-time secrets are never stored for replay; for short-lived upload/download grants, replay returns the same pending/resource identity with a freshly minted grant, not a stored URL.
- **Retention (v1 technical proposal):** completed public-intake records are retained at least 24 hours; completed authenticated create/action records at least 7 days. After expiry the same key is treated as a new intent. Cleanup and any longer retention are `TBD-TECH-03`. A stored record contains only scope, key fingerprint as required by the adapter, payload hash, state/lease, HTTP status, minimal safe response/resource ID, and created/expires timestamps — never passwords, invitation/reset tokens, provider payloads, or raw request bodies.
- Every mutable aggregate DTO carries `version: integer` (`ro`). An input `version` is the expected current version, not a client-chosen new value; the server increments it on successful aggregate change. Stale values return `409 CONFLICT_VERSION`. Creates do not accept `version` and return `version: 1` where the aggregate is versioned. Immutable event records (for example progress measurements and diary entries) have no update endpoint and therefore need no version.
- Notification sending is at-least-once at the worker level and effectively-once per business event via outbox idempotency (§7).

### 1.9 Rate limiting & abuse (public + auth surfaces)
- Public intake, login, invitation-accept, and password-reset endpoints MUST be rate-limited by IP + relevant identifier, backed by shared storage (the baseline’s in-process `Map` limiter is explicitly insufficient across serverless instances). Exact thresholds `TBD-TECH-03`; behavior on limit: `429` + `Retry-After`, no record created.
- Anti-spam for public forms (honeypot and/or challenge) is `TBD-TECH-03`; the contract reserves an optional `challengeToken` field so enabling it is non-breaking.

### 1.10 Persistence notation (used in every endpoint block)
- `READ` — no business, audit-log, outbox, export-job, or storage-metadata writes. Ordinary GET list/detail/status reads MUST be `READ`; security/access telemetry outside the business audit log does not change this classification.
- `AUDIT-ONLY` — the sole permitted GET audit exception, used only for the protected document-download authorization in §3.7: one `document.downloaded` audit append, no business-state change. No other GET may use this notation without a contract amendment.
- `TX[ a + b + audit + outbox(ev) ]` — all listed writes commit or roll back **atomically** inside one `UnitOfWork` (§5.2); the success response is returned only after commit. `audit` = audit-log entry (§6 SEC-09). `outbox(ev)` = notification intent rows for event(s) `ev` (§7) — **sending is asynchronous and never part of the request’s success condition.**
- `EXTERNAL[storage]` — interaction with the `FileStorage` port outside the DB transaction; failure must not leave half-written business state (create metadata only after confirmed upload, or mark-and-reconcile — adapter/service design note in §5.3).

## 2. DTO dictionary

Field optionality: `!` required, `?` optional, `ro` server-set/read-only. Validation references (V-…) are defined in Appendix A and mirror the rules already implemented in `src/lib/validation.ts` — server validation MUST be at least as strict.

#### DTO ownership, writable subsets, and PATCH semantics (normative)
- A response DTO is **never** a request body. Every mutation names a `*Input` DTO in §2 or an explicitly empty body in §3. Only fields listed in that input are client-writable.
- Server-owned fields include IDs, references, all created/updated/status/event timestamps unless an input explicitly defines a reported event time, actor/creator/recorder IDs, `source`, session-derived `customerId`, derived totals/progress/statuses, audit/history/provider data, storage keys, and invitation/reset secrets. Sending one in an input is `422` (`readOnly`), not an ignored value.
- For PATCH: an omitted field is unchanged; explicit `null` clears a field only where the input says “nullable”; arrays are replaced atomically as a whole unless the endpoint explicitly defines keyed partial updates. A PATCH containing no writable change besides `version` returns `422 VALIDATION_FAILED` with `details.reason: "EMPTY_PATCH"`.
- Target-state fields are writable only to request a transition listed in §4; the server sets all resulting status timestamps/actors. Action inputs state whether expected `version` is required. Child creation does not accept a parent `version` unless the endpoint also changes the parent aggregate.
- Unprefixed DTOs in §2.2–§2.7 are staff/admin projections unless explicitly public/auth DTOs. Portal endpoints MUST use the separate `Portal*DTO` projections in §2.8; any field not listed there is unavailable to customers until `TBD-PO-08` approves it. Staff list endpoints use summary DTOs where named, not detail DTOs with fields informally “omitted.”

### 2.3 Identity
- **UserDTO**: `id ro`, `email`, `phoneE164?`, `displayName`, `role` (§1.3), `status: 'invited'|'active'|'disabled'`, `customerId?` (present iff role=`CUST`), `createdAt ro`, `updatedAt ro`, `lastLoginAt? ro`, `version ro`. Password hashes/tokens/session identifiers never appear in any DTO.
- **CreateStaffUserInput**: `email! (V-EMAIL-REQ)`, `displayName!`, `role!` (staff roles only), `phoneE164? (V-PHONE)`, `activation! { channel!: 'email'|'whatsapp', locale!: 'ar'|'en' }`. The server creates the user as `invited`; no password or activation secret is accepted or returned by this endpoint. Which activation channels are enabled follows `TBD-PO-01`/`TBD-TECH-08`; an unsupported channel is `422`.
- **UpdateUserInput**: `displayName?`, `phoneE164? nullable`, `role?` (staff roles only; never to/from `CUST` through this endpoint), `status? ('active'|'disabled' only; 'invited' is server-owned)`, `version!`. Email is not writable here because an email-change verification flow is `TBD-TECH-01`.
- **InvitationDTO**: `id ro`, `subject ro` — exactly one of `{ kind: 'staff', userId }` or `{ kind: 'customer', customerId }` — `channel: 'whatsapp'|'email'`, `locale`, `status: 'pending'|'accepted'|'expired'|'revoked'`, `expiresAt ro`, `createdBy ro`, `createdAt ro`, `version ro`. The secret token is transmitted only inside the delivered link, stored hashed, and never returned by any GET or create response.
- **CreateCustomerInvitationInput**: `channel!`, `locale!`. The destination is derived by the server from the identified customer's stored email/phone; staff cannot override the destination through this input. Missing destination for the chosen channel is `422`; consent/channel enablement follows `TBD-PO-01`.
- **InvitationRevokeInput**: `version!`. **AcceptInvitationInput**: `token!`, `password! (V-PASSWORD)` only — the token's server-side subject determines whether an invited staff user is activated or a customer portal user is created; display name comes from the existing staff/customer record and can later be changed through an approved profile flow.
- **PasswordResetRequestInput**: `identifier!` (email or phone). **PasswordResetConfirmInput**: `token!`, `newPassword! (V-PASSWORD)`. **ChangePasswordInput**: `currentPassword!`, `newPassword!`. Token-redemption and password endpoints do not carry aggregate `version`; single-use token state, password verification, and session-generation revocation are their concurrency controls.

### 2.4 Customers, requests, inspections
- **CustomerDTO**: `id ro`, `reference ro`, `name`, `phoneE164`, `email?`, `city?`, `whatsappConsent { granted: boolean, at?, source? } ro`, `portalUserIds ro[]`, `createdAt ro`, `updatedAt ro`, `version ro`. Note: today’s UI *derives* a customer status from their latest request/projects; this spec keeps that as a read-model field `derivedStatus? ro` computed by the service — it is never client-writable. Whether customers also need a stored lifecycle status is `TBD-PO-03` (do not invent one).
- **CustomerCreateInput**: `name! (V-NAME)`, `phoneE164! (V-PHONE; normalized server-side)`, `email? (V-EMAIL)`, `city?`. It does **not** accept WhatsApp consent, `derivedStatus`, `portalUserIds`, reference, or timestamps; consent can be set only by an approved capture flow (`TBD-PO-01`), never asserted silently by staff create.
- **CustomerUpdateInput**: `name?`, `phoneE164?`, `email? nullable`, `city? nullable`, `version!`. Phone uniqueness/merge policy is `TBD-PO-12` — until decided, create/update MUST NOT silently merge customers; whether a duplicate is rejected with `422 fieldErrors.phoneE164:['duplicate']` or handled by an explicit staff link/merge workflow remains blocked by that decision.
- **RequestSummaryDTO**: `id ro`, `reference ro`, `customerId?` (`null` until staff explicitly link the public intake record to a customer), `customerName ro` (linked customer name when present, otherwise the submitted full name), `serviceSlug`, `city`, `submittedAt ro`, `status` (§4.1), `priority`, `assigneeId?`, `assigneeName? ro`, `version ro`.
- **RequestDetailDTO** = summary + `phoneE164` (staff only), `email?`, `areaM2?`, `unitType?`, `description`, `consent: ConsentRecordDTO ro`, `history: RequestHistoryEntryDTO[]`, `workflow { stages: {key, state, evidenceRefs[]}[], nextAction, blockers[] } ro` (same derivation semantics as the current tested preview logic, recomputed server-side), `context { inspections: InspectionDTO[], quotations: QuotationSummaryDTO[], sameCustomerProjects: ProjectSummaryDTO[], sameCustomerContracts: ContractSummaryDTO[] } ro`. **Same-customer context is informational only and MUST NOT be presented or treated as workflow evidence** (existing product rule).
- **RequestHistoryEntryDTO**: `status`, `at ro`, `actorId ro`, `note?`.
- **LinkRequestCustomerInput**: `customerId!`, `version!`. This is the only v1 operation that sets `Request.customerId`; it links to an existing customer and does not create, merge, or silently deduplicate customers.
- **RequestUpdateInput**: `status?` (manual targets only: `contacted`, `on_hold`, the computed resume status from `on_hold`, or `cancelled`), `assigneeId? nullable` (null unassigns), `priority?`, `note?`, `version!`. At least one of `status`/`assigneeId`/`priority` MUST be present; `note` alone is not a mutation. Evidence-backed statuses (`inspection_scheduled`, `inspection_done`, `quotation_sent`, `approved`) are **not** writable through this generic input — §4.1 makes them server side-effects of the linked inspection/quotation/customer-decision operations. The server also enforces V-ASSIGNEE (Appendix A): a request cannot enter/remain in an inspection stage without an assignee.
- **InspectionResultDTO**: `notes`, `completedAt ro`, `completedBy ro`. No opaque `measurements` object is part of v1: the measurement/result capture schema is `TBD-PO-13` and must be added as typed fields by contract amendment before completion can be implemented.
- **InspectionDTO**: `id ro`, `reference ro`, `requestId`, `customerId? ro` (copied/derived from the request link; may be null for an as-yet-unlinked public intake request), `serviceSlug ro`, `scheduledAt`, `engineerId`, `status: 'inspection_scheduled'|'inspection_done'|'cancelled'`, `result?: InspectionResultDTO`, `version ro`. Whether `cancelled` is an allowed inspection outcome and what happens to the parent request are unresolved in `TBD-PO-13`; until approved, the value is reserved and no endpoint may transition to it.
- **InspectionCreateInput**: `requestId!`, `scheduledAt!` (future), `engineerId!`. Customer/service/status are server-derived from the request.
- **InspectionResultInput**: `notes!` plus only the typed measurement fields later approved under `TBD-PO-13`. **InspectionUpdateInput**: `scheduledAt?`, `engineerId?`, `status?`, `result?: InspectionResultInput`, `version!`. Valid combinations are: reschedule/reassign only while `inspection_scheduled`; `status:'inspection_done'` requires `result` in the same request and forbids simultaneous reschedule/reassign; no other target status is writable in v1. Completed inspections are immutable through this input.

### 2.5 Quotations & contracts
- **QuotationItemInput** (the only client-writable item shape): `description!`, `unit!` (free-text unit label), `quantity!` (>0, up to 3 decimals), `unitPriceMinor!` (≥0 integer). It has no item ID or line total.
- **QuotationItemDTO**: `id ro` + the `QuotationItemInput` fields + `lineTotalMinor ro` (server-computed). Client-sent IDs/totals are rejected as read-only/unknown according to §2 DTO rules.
- **QuotationRevisionDTO** (one immutable commercial snapshot once sent): `revisionNo ro`, `title`, `items: QuotationItemDTO[]`, `totals { subtotalMinor ro, taxMinor? ro, totalMinor ro }` (tax existence/rate `TBD-PO-04`; until decided `taxMinor` is omitted, never zero-filled misleadingly), `validUntil?`, `internalReview { status: 'not_submitted'|'pending'|'approved'|'changes_requested'|'not_required', submittedBy? ro, submittedAt? ro, decidedBy? ro, decidedAt? ro, note? ro }`, `delivery { status: 'not_sent'|'sent', sentAt? ro, sentBy? ro }`, `customerDecision: null | { outcome: 'approved'|'rejected', decidedAt ro, recordedAt ro, actorKind: 'customer'|'recorded_by_staff' ro, customerUserId? ro, recordedByUserId? ro, comment? ro }`, `decisionEligibility: 'not_sent'|'actionable'|'decided'|'superseded'|'expired' ro` (derived; **`superseded` applies only to a sent revision with `customerDecision:null` that was replaced before a decision — a decided revision remains `decided` forever**), `contractEligibility: 'not_eligible'|'eligible'|'superseded' ro` (separate derived staff-only commercial eligibility: only a customer-approved revision can be `eligible`; under the `TBD-PO-04A` Q2 option a later sent revision can make it `superseded` without changing `customerDecision` or `decisionEligibility`), `createdBy ro`, `createdAt ro`. `not_required` may be set only by the server's approved `TBD-PO-04` review policy; clients can never write any part of `internalReview`, `delivery`, `customerDecision`, or either eligibility field directly.
- **QuotationDTO** (staff detail): `id ro`, `reference ro`, `requestId?`, `customerId`, `projectId? ro` (set after project creation), `currency ro` (server configuration, `TBD-PO-04`), `currentRevisionNo ro`, `currentRevision: QuotationRevisionDTO`, `revisionSummaries: QuotationRevisionSummaryDTO[] ro`, `createdAt ro`, `updatedAt ro`, `version ro`. There is intentionally **no** top-level quotation `status`; staff UI derives a display label from the current revision's three separate dimensions.
- **QuotationRevisionSummaryDTO**: `revisionNo`, `title`, `totalMinor`, `validUntil?`, `internalReviewStatus`, `deliveryStatus`, `customerDecisionOutcome?`, `decisionEligibility`, `contractEligibility`, `createdAt`. **QuotationSummaryDTO** (staff lists/context): `id`, `reference`, `requestId?`, `customerId`, `customerName ro`, `title` (current revision), `currency`, `currentRevisionNo`, `internalReviewStatus`, `deliveryStatus`, `customerDecisionOutcome?`, `decisionEligibility`, `contractEligibility`, `totals`, `validUntil?`, `updatedAt`, `version`.
- **QuotationCreateInput**: exactly one of `requestId!` (customer derived from that request) or `customerId!`; `title!`; `items!: QuotationItemInput[]` (≥1); `validUntil?`. The server creates revision 1 with delivery `not_sent`, customer decision `null`, and internal-review status evaluated from the approved `TBD-PO-04` policy (`not_submitted` when review is required; `not_required` only when that policy says so).
- **QuotationUpdateInput**: `revisionNo!` (must be current), `title?`, `items?: QuotationItemInput[]` (whole-array replacement, ≥1 if present), `validUntil? nullable`, `version!`. It is valid only for an unsent, unlocked current revision (`internalReview.status` ∈ `not_submitted|changes_requested|not_required`); editing a `changes_requested` revision resets internal review to `not_submitted`, and editing a `not_required` revision re-evaluates the approved review policy. Pending/approved/sent revisions return `409 CONFLICT_STATE`.
- **QuotationRevisionCreateInput**: `sourceRevisionNo!` (must be the current sent-undecided — including expired — or customer-rejected revision; a **customer-approved source is conditional and blocked until `TBD-PO-04A` is selected**, see §4.2), `title?` (defaults to source title), `items!: QuotationItemInput[]`, `validUntil? nullable`, `internalNote?` (staff-only audit context; never returned by portal DTOs), `version!`. It creates the next revision with internal review reset by policy, delivery `not_sent`, customer decision `null`, and contract eligibility `not_eligible`; it does not mutate, decision-supersede, or contract-supersede the source revision and never transfers a prior approval.
- **QuotationSubmitForReviewInput**: `revisionNo!`, `note?`, `version!`. **QuotationInternalReviewDecisionInput**: `revisionNo!`, `outcome!: 'approved'|'changes_requested'`, `note?` (required when outcome is `changes_requested`), `version!`. **QuotationSendInput**: `revisionNo!`, `version!` — no client-chosen channel/status; the approved customer-access/notification path is server policy under `TBD-PO-01/04`.

The customer and quotation ownership come from the session/path authorization, never the body. **RecordCustomerDecisionInput** (staff-recorded off-portal decision; endpoint exists only if `TBD-PO-04` approves this channel): `revisionNo!`, `outcome!`, `customerDecisionAt!` (reported decision time), `evidenceNote!`, `evidenceDocumentId?` (must be a finalized document owned by the quotation/customer context approved for evidence), `version!`. Server `recordedAt`/recorder are separate from the reported customer decision time; required evidence and who may record it remain `TBD-PO-03/04`.
- **ContractSummaryDTO**: `id`, `reference`, `quotationId`, `quotationRevisionNo`, `customerId`, `customerName ro`, `projectId?`, `type`, `baseAmountMinor`, `effectiveAmountMinor ro`, `currency`, `status`, `updatedAt`, `version`.
- **ContractDTO**: `id ro`, `reference ro`, `quotationId`, `quotationRevisionNo ro`, `customerId ro`, `projectId? ro`, `type`, `baseAmountMinor ro` (snapshot from the customer-approved quotation revision), `approvedChangeOrdersTotalMinor ro`, `effectiveAmountMinor ro` (= base + approved change-order deltas), `currency ro`, `status: 'draft'|'pending_signature'|'signed'`, `issuedAt? ro`, `issuedBy? ro`, `issuedDocumentId? ro`, `signature?: { signedAt ro, signMethod ro, evidenceDocumentId? ro, recordedAt ro, recordedBy ro }`, `documentIds ro[]` (staff projection only), `createdAt ro`, `updatedAt ro`, `version ro`. The API records issuance/signature evidence; it does not define legal validity (`TBD-PO-05`).
- **ContractCreateInput**: `quotationId!`, `quotationRevisionNo!`, `expectedQuotationVersion!`, `type!`. Amount/customer/currency are server-derived snapshots; no other contract fields are writable at creation. **ContractUpdateInput**: `type?`, `version!` — draft only. **ContractIssueForSignatureInput**: `documentId?`, `version!`; if present, the document MUST be finalized and owned by this contract. Whether a final issuance document is mandatory, and what it must contain, is `TBD-PO-05`, so this input cannot freeze until that decision is made. **RecordContractSignatureInput**: `signedAt!` (reported signing time), `signMethod!` (enum fixed only by `TBD-PO-05`), `evidenceDocumentId?` (finalized contract-owned document if the chosen method produces evidence), `version!`; server records `recordedAt`/`recordedBy` separately.
- **ChangeOrderDTO**: `id ro`, `contractId ro`, `description`, `amountDeltaMinor` (may be negative), `durationDeltaDays?`, `decisionStatus: 'pending'|'approved'|'rejected'`, `decision?: { outcome, actorId ro, actorKind ro, at ro, note? ro }`, `createdBy ro`, `createdAt ro`, `version ro`. **ChangeOrderCreateInput**: `description!`, `amountDeltaMinor!`, `durationDeltaDays?` only. **ChangeOrderDecisionInput**: `outcome!: 'approved'|'rejected'`, `note?`, `version!`. Whether the decision actor is staff, the customer, or both in sequence is unresolved (`TBD-PO-03/04`); therefore this DTO/endpoint is not implementation-ready as a customer-approval mechanism and MUST NOT be presented as one.

### 2.6 Projects & operations

Integrity rules: `pending` requires resulting progress `0`; `in_progress` requires `0–99`; setting `completed` sets progress to `100` and `completedAt` server-side; `progressPercent:100` without `completed` is `422`; completed milestones are immutable through this input unless a later approved correction policy says otherwise.

Storage keys/URLs never appear in DTOs.

## 3. Endpoint catalog (proposed)

Global endpoint rules: every POST below requires `Idempotency-Key` and can return the §1.8 idempotency errors, except the expressly exempt password/token endpoints and the provider webhook. Every PATCH/action on a versioned aggregate requires the input `version` named in §2. Staff **Auth** lists are provisional role sets; the resource predicates and unresolved authorities in §3.11 are part of authorization and may further deny access. “No body” means no JSON object fields are accepted; sending fields is `422 unknownField`.

### 3.1 Public intake
**POST `/api/v1/public/inspection-requests`** — Auth: PUB (+ rate-limit/anti-spam §1.9) · Req: `InspectionRequestCreateInput` · Res: `201 IntakeReceipt` · Validation: Appendix A in full, server-side; `serviceSlug` MUST be a published service · Errors: 400, `IDEMPOTENCY_*`, 422, 429, 503 · Persistence: `TX[intake request + status history('new') + audit('request.created', actor=public) + outbox(staff_alert, customer_confirmation)]`. Intake does not silently create/merge a `Customer`; customer linkage/creation is an explicit staff workflow governed by `TBD-PO-12`. Response only after commit. **WhatsApp availability never affects this response.**

**POST `/api/v1/public/contact-messages`** — Auth: PUB (same protections) · Req: `ContactMessageCreateInput` · Res: `201 IntakeReceipt` · Validation: V-NAME/V-PHONE/V-MSG + subject allow-list · Errors: as above · Persistence: `TX[contact_message + audit('contact_message.created', actor=public) + outbox(staff_alert)]`.

### 3.2 Identity & accounts
**GET `/api/v1/me`** — Auth: any signed-in user · Res: `200 UserDTO` for the session user only · Errors: CE-AUTH · Persistence: READ.
**POST `/api/v1/auth/password-reset/request`** — Auth: PUB + rate-limit; idempotency-exempt · Req: `PasswordResetRequestInput` · Res: `202 { accepted: true }` always (no account enumeration) · Errors: 400, 422 (identifier shape only), 429, 500 · Persistence: if and only if an eligible account exists, `TX[reset_token(hashed, expiry) + outbox(reset_link) + audit('auth.password_reset_requested')]`; otherwise no business write. The response is identical either way.
**POST `/api/v1/auth/password-reset/confirm`** — Auth: PUB + rate-limit; idempotency-exempt (single-use token) · Req: `PasswordResetConfirmInput` · Res: `204` · Errors: `TOKEN_*`, 422 (V-PASSWORD), 429 · Persistence: `TX[password_hash update + token consumed + all sessions revoked + audit('auth.password_reset_completed')]`.
**POST `/api/v1/auth/change-password`** — Auth: signed-in; idempotency-exempt · Req: `ChangePasswordInput` · Res: `204` · Errors: 401, 422 (wrong current password → `fieldErrors.currentPassword`), 429 if the auth limiter applies · Persistence: `TX[hash update + other sessions revoked + audit('auth.password_changed')]`.
**GET `/api/v1/admin/users`** — Auth: OWN (provisional; user-admin authority §3.11) · Res: `Page<UserDTO>`; filters `role`, `status`, `search` · Errors: CE-LIST · Persistence: READ.
**POST `/api/v1/admin/users`** — Auth: OWN · Req: `CreateStaffUserInput` · Res: `201 UserDTO` with `status:'invited'` · Validation: unique normalized email (`422 fieldErrors.email:['duplicate']`), staff role only, enabled activation channel/destination · Errors: CE-STD + `IDEMPOTENCY_*` · Persistence: `TX[user(invited) + staff invitation(hashed token, expiry) + outbox(staff_activation) + audit('user.created')]`.
**PATCH `/api/v1/admin/users/{userId}`** — Auth: OWN · Req: `UpdateUserInput` · Res: `200 UserDTO` · Errors: CE-STD + `409 CONFLICT_VERSION`; changing own role/disabling self in a way that removes the last usable owner access → `422` with `details.reason:'SELF_LOCKOUT'` (exact owner-recovery policy remains in `TBD-PO-03`/`TBD-TECH-01`) · Persistence: `TX[user (+ session revocation when disabled or role/security-relevant fields change) + audit('user.updated')]`.

## 4. Workflow state machines (proposed; transitions are server-enforced)

**4.1 Inspection request.** The state graph preserves the current tested vocabulary: `new → contacted → inspection_scheduled → inspection_done → quotation_sent → approved`; from any non-terminal state `→ on_hold` (resume returns to the last non-hold status, with `new` resuming to `contacted`) and `→ cancelled`. Terminal: `approved`, `cancelled`.
- Generic `PATCH /admin/requests/{id}` may perform only manual contact/hold/resume/cancel transitions and assignment/priority changes.
- Evidence-backed transitions are server side-effects only: creating a linked inspection performs `contacted→inspection_scheduled`; completing it performs `inspection_scheduled→inspection_done`; first sending a linked quotation performs `inspection_done→quotation_sent`; later pre-approval revision sends leave `quotation_sent` unchanged with no duplicate history entry; customer approval of an actionable sent revision while the request is `quotation_sent` performs the one terminal transition `quotation_sent→approved`.
- **Terminal-state rule:** once a request is `approved` (or `cancelled`), no quotation revision creation/send/decision, contract creation/issuance/signing, or project action may change its status or append a request status-history entry. In particular, there is no implicit `approved→quotation_sent` reopening. If `TBD-PO-04A` option Q2 or Q3 is selected, post-approval quotation sends/decisions are quotation-only effects while the request simply remains `approved`.
- Customer rejection, internal quotation approval, same-customer records, and staff assertions without the dedicated (conditional) recorded-decision operation MUST NOT move a request to `approved`. This prevents status-only workflow evidence and preserves the repository rule that only explicit linked records support progression.

**4.2 Quotation revision — three independent dimensions.** There is no single quotation lifecycle `status` and no API state in which `approved` can mean two actors' decisions.

| Dimension / event | Valid transition | Locking / eligibility / audit |
|---|---|---|
| Create revision | internal `not_submitted` **or** policy-derived `not_required`; delivery `not_sent`; customer decision `null` | Editable while unsent and internal status is `not_submitted\|changes_requested\|not_required`; audit `quotation.created` or `quotation.revision_created`. |
| Edit current revision | same revision only; `changes_requested → not_submitted` after an edit; `not_required` is re-evaluated under PO-04 | Forbidden when internal `pending\|approved` or delivery `sent`; totals server-recomputed; audit `quotation.revision_updated`. |
| Submit for internal review | internal `not_submitted\|changes_requested → pending` | Only when approved PO-04 policy requires review; revision becomes locked; audit `quotation.internal_review_submitted`. |
| Internal review decision | internal `pending → approved` or `pending → changes_requested` | `approved` remains locked and becomes send-eligible subject to other checks. `changes_requested` unlocks the same unsent revision and requires a note. Neither outcome changes delivery, customer decision, or linked request status; audit `quotation.internal_review_decided` with outcome/actor. |
| Send to customer | delivery `not_sent → sent` | Requires internal `approved\|not_required`, exact revision/version, valid items/totals/validity/customer/linked-request checks §3.5. Sets `sentAt/sentBy`, locks the revision snapshot, initializes no customer decision, and audits `quotation.sent`. |
| Decision-supersede prior undecided sent revision | prior **actionable** undecided sent revision `actionable → superseded` when a newer revision is sent | One-actionable-revision rule. An already-**expired** undecided revision remains `expired`, and a **decided** revision remains `decided` forever. Creating (not sending) a draft does not supersede anything. The superseded snapshot remains readable but cannot receive a decision; audit `quotation.revision_superseded` in the send transaction. This row governs decision eligibility only and does not by itself invalidate a customer-approved revision. |
| Customer decision | customer decision `null → approved` or `null → rejected` on the actionable sent revision | Terminal for that revision; repeat genuine attempts are `409`; idempotent replay returns the original result. If the linked request is `quotation_sent`, approval moves it once to terminal `approved`; if it is already `approved` under selected Q2/Q3, approval or rejection leaves it `approved` with no request history. Rejection has no automatic request transition in either case. Internal-review history and every earlier decision are unchanged. Audit `quotation.customer_decided` (portal) or `quotation.customer_decision_recorded` (conditional staff-recorded channel). |
| Create next revision after send/decision | source revision unchanged → new revision with internal reset, delivery `not_sent`, decision `null`, contract eligibility `not_eligible` | Allowed in the base contract from a sent-undecided/expired or customer-rejected source. From a **customer-approved** source it is blocked until `TBD-PO-04A` is selected (Q1 rejects; Q2/Q3 allow). A prior approval never transfers. If an unsent draft was created before its source was approved, the draft remains unsent/unapproved and its later send is governed by the post-approval gate. |
| Expiry | derived `decisionEligibility: expired` only for an undecided sent revision when an approved `validUntil` policy says it is no longer actionable | Expiry is not a customer/internal decision and MUST NOT overwrite either. A decided revision never becomes `expired`. Sending a replacement after expiry leaves the earlier revision `expired` (not decision-superseded). If a Q2 post-approval replacement later expires, the earlier approved revision does **not** regain contract eligibility; under Q3 it was never lost. Exact validity/expiry business behavior remains `TBD-PO-04`. |

**Post-customer-approval revision policy (`TBD-PO-04A`) — owner must select exactly one option.** The following invariants apply under every option: a customer decision is immutable and revision-specific; a decided revision is never decision-superseded or expired; approval never transfers to another revision; merely creating an unsent revision changes neither the source's contract eligibility nor the request; and a linked `approved` request remains terminal `approved` with no further request status/history changes. Until one option is selected, the base contract **blocks** both `POST /admin/quotations/{id}/revisions` from a customer-approved source and `POST /admin/quotations/{id}/send` whenever an earlier revision of that quotation is customer-approved (including a draft created before that approval). Consequently no post-approval portal/recorded decision sequence is reachable in the unselected base. Separately, a quotation with no customer-approved revision cannot be sent against an already-`approved` linked request under any Q option; Q1/Q2/Q3 govern revisions of the already-approved quotation, not an unspecified second quotation attached to a terminal request.
- **Q1 — No same-quotation revision after customer approval.** Revision creation from an approved source is rejected, and an unsent draft created earlier cannot be sent after its source is approved. The approved revision remains contract-eligible, and a draft contract created from it remains eligible for issuance subject to PO-05. Any later commercial change must use a separate process the owner approves (for example a new customer-direct quotation or new request, or a contract change mechanism); attaching/sending another quotation against the same terminal request is not specified here.
- **Q2 — Replacement revision may be sent and supersedes the prior approval for contract eligibility only.** Revision creation/send after approval are allowed as quotation-only effects. At the moment the newer revision is sent, every earlier customer-approved revision keeps `customerDecision.outcome:'approved'` and `decisionEligibility:'decided'`, but its `contractEligibility` becomes `superseded`; creating a new contract from it and issuing an existing **draft** contract based on it are then denied. Rejection or expiry of the newer revision does not restore the earlier eligibility. A newer revision becomes contract-eligible only by its own customer approval. The owner must also choose the already-issued-contract sub-option: **Q2a** grandfather a `pending_signature` contract so `mark-signed` may proceed, or **Q2b** block `mark-signed` after the superseding send. Already-`signed` contracts are never changed by a later quotation send.
- **Q3 — Replacement revision may be sent without invalidating the prior approval.** Revision creation/send after approval are allowed as quotation-only effects; the earlier approved revision remains contract-eligible and an existing draft contract based on it remains eligible for issuance. If the newer revision is also customer-approved, each approved revision is independently contract-eligible and every contract operation must name the exact revision; intentional contract multiplicity remains governed by `TBD-PO-19`. Already-issued/signed contracts are unaffected.

No hard internal “reject/terminate quotation” transition, withdrawal of a sent revision, customer decision reversal, or expiry consequence is specified until PO-04 defines those business outcomes.

**4.3 Contract and change orders.** Contract lifecycle is exactly `draft → pending_signature → signed`:
- `POST /admin/contracts` creates **draft** only from one exact revision whose customer decision is `approved` **and** whose derived `contractEligibility` is `eligible` at commit; it snapshots amount/customer/currency. An unsent newer quotation draft does not affect that eligibility.
- Draft `type` (and contract-owned documents through §3.7) may be prepared while draft. Amount/customer/quotation snapshots cannot be patched.
- `POST /admin/contracts/{id}/issue-for-signature` is the only `draft→pending_signature` transition. It rechecks that the exact source revision remains customer-approved and `contractEligibility:'eligible'`, records `issuedAt/issuedBy` and the optional/required issuance document according to `TBD-PO-05`, and audits `contract.issued_for_signature`. Under Q2, a newer quotation revision sent after draft creation makes issuance fail with `409 SOURCE_REVISION_CONTRACT_SUPERSEDED` while leaving the draft contract unchanged; under Q3 it does not; under Q1 that sequence cannot occur.
- `POST /admin/contracts/{id}/mark-signed` is the only `pending_signature→signed` transition. It records reported signing time/method/evidence separately from server recording actor/time and audits `contract.signature_recorded`. A later quotation send never automatically changes a `pending_signature` or `signed` contract; under Q2, whether an already-issued contract may still be signed after its source becomes contract-superseded is the Q2a/Q2b sub-decision in `TBD-PO-04A`. Direct `draft→signed`, backward correction, cancellation, voiding, and amendment transitions are **not** in v1; whether any are needed and who may use them is `TBD-PO-05/19`. The API does not decide what legally constitutes a signature.
- Change orders have a separate `pending → approved|rejected` decision state and do not change contract lifecycle status. The base contract amount snapshot never changes; approved deltas affect only the derived effective amount. Decision actor(s) remain `TBD-PO-03/04`.

**4.4 Project and operational records.** Project: created `in_progress`; manual `in_progress ⇄ on_hold`; manual `in_progress|on_hold → cancelled` with a required cancellation note/audit; `in_progress|on_hold → handed_over` **only** as the atomic side-effect of handover completion. Terminal: `handed_over`, `cancelled`. Milestones: `pending → in_progress → completed` with the progress invariants in §2.6. Findings: `open → in_progress → resolved`; no reopen transition is specified. Reports: `draft → pending` (submit-for-review) `→ approved` (internal approve) `→ sent` (publish); no return/reject path is invented. Handover: `pending → handed_over` only through completion. Warranty: `open → in_progress → resolved`, with `resolutionNote` required at resolution. Diary entries and progress measurements are immutable records without lifecycle transitions.

**4.5 Notification:** `queued → sending → sent → delivered → read`; failure path `… → failed → queued (retry, bounded) → dead` (§7). Provider may not supply every state; missing states are skipped, never fabricated. Manual review does not change delivery status.

**4.6 Audit export:** `pending → processing → ready|failed`; `ready → expired` when its retention time passes. Requesting a download link does not change export status. Ordinary audit-log reads and export-status reads have no state transition and append no audit entry; export request/ready/failed/download-grant events are the audited actions in §3.9.

## 5. Repository ports & transaction boundary (database-independent)

### 5.1 Layering rule
`Route handlers/Server Actions` (auth + DTO validation only) → `Application services` (business rules, §4 transitions, audit/outbox decisions) → **ports below** → colleague’s adapter (their DB/ORM) **or** the dev/test fake adapter. Services MUST NOT import any ORM/driver/SQL. Ports exchange DTOs (§2) and typed query objects (`PageQuery` + per-aggregate filters) — never ORM entities.

### 5.2 UnitOfWork (transaction boundary)
Conceptual shape:
```
interface UnitOfWork {
  run<T>(work: (repos: Repositories) => Promise<T>): Promise<T>;
}
```
Semantics the adapter MUST guarantee (verified by CT-PORT tests, §8): atomic commit/rollback across **all** repository writes in `work` including audit and outbox rows; read-your-own-writes inside the transaction; optimistic `version` checks raise a typed `VersionConflict` domain error (mapped to `409 CONFLICT_VERSION`); no partial business side-effects on throw. For idempotent POSTs, the scoped `IdempotencyStore` claim is taken before `work`; completion MUST be recorded only for the committed result, while rollback/retryable failure releases or marks the claim retryable so a committed business effect and its replay record cannot diverge silently. The colleague may implement the claim inside or alongside their transaction mechanism, but the observable §1.8 behavior (one execution, safe replay, concurrent duplicate does not execute) is contractual. How this maps to the colleague’s engine (native transactions, isolation level) is `TBD-DB-05` — the *behavior* is contractual, the mechanism is theirs.

## 6. Security rules (normative)

- **SEC-01 Customer isolation:** every portal read/write is scoped by `customerId` taken from the authenticated session — never from path/body/query. Single-record access by foreign ID returns `404`. List endpoints filter by owner *in the query*, not by post-filtering in the UI.
- **SEC-02 Server-side authorization:** every handler checks authentication, role, and (where applicable) assignment/ownership on the server. Middleware is a first fence, never the only one (mirrors the baseline’s layout+middleware double-check).
- **SEC-03 Staff scoping:** staff authorization is role **plus** resource predicate. Assignment/parent-resource/separation predicates in §3.11 are unresolved (`TBD-PO-03`); until approved and encoded as testable service rules, an endpoint MUST NOT fall back to “any STAFF may access everything.” In particular, PM/QA project access cannot be called assignment-scoped until the project-assignment source is defined.
- **SEC-04 Public intake:** server validation ≥ UI validation (Appendix A), rate limits, anti-spam hook, idempotency keys, payload size caps, and no reflection of submitted data into staff notifications beyond reference + admin link (staff open the record in the authenticated dashboard).
- **SEC-05 Tokens:** invitation/reset secrets are ≥128-bit random, stored hashed, single-use, short-lived, and rate-limited on redemption; issuing a new invitation revokes prior pending ones.
- **SEC-06 Passwords & sessions:** strong KDF hashing (existing scrypt approach or argon2id — `TBD-TECH-01`), no plaintext anywhere, sessions revocable per user, login/reset/accept endpoints rate-limited from shared storage, auth errors non-enumerating.
- **SEC-07 Files:** private storage and `visibleToCustomer=false` by default; staff upload/download requires authority on the document's parent entity, not merely a staff session. Customer download requires session-customer ownership of the parent context **and** the visibility flag, current version only. Downloads use authorized API → short-lived signed URLs; upload type/size allow-lists are enforced at signing **and** verified at finalize (`head`); uploaded content is never executed or served inline from the app origin.
- **SEC-08 Notification content minimization:** WhatsApp/email bodies carry event + reference + authenticated link only — no amounts, line items, addresses, or document contents.
- **SEC-09 Audit:** append-only audit for: auth events, user/invitation lifecycle, all status transitions and decisions, publish/visibility changes, successful protected-document downloads, audit-export request/completion/failure/download-grant, retries/manual notification actions, role/status changes. Audit writes participate in the same transaction as the action they record (an unaudited sensitive action must be impossible). Ordinary GET reads — including audit-log list and export-status polling — MUST NOT append audit entries; denied/export-not-ready attempts go to security telemetry rather than polluting or recursively growing the business audit log. The only GET audit exception is the explicitly labelled document-download `AUDIT-ONLY` case.
- **SEC-10 Webhooks:** provider signature verification before any processing; replay/duplicates are idempotent no-ops; webhook payloads are treated as untrusted input.
- **SEC-11 Secrets & config:** secrets only via environment/secret manager; env **names** are documented (§10) — values never enter chat, repo, logs, or DTOs. Logs redact tokens, passwords, and full phone numbers.
- **SEC-12 PII/response minimization:** list views use summary DTOs; full phone numbers only to roles that need them (`TBD-PO-03` may narrow further); audit `before/after` excludes secrets and oversized free text. Portal serialization is allow-list based on §2.8 only — reusing a staff DTO on a portal endpoint is forbidden, and any field pending `TBD-PO-08` remains omitted.
- **SEC-13 Transport/platform:** HTTPS-only cookies as in baseline; security headers and CORS default-deny for `/api/v1` (same-origin app only, unless PO approves a named external client).

## 7. Notification outbox & delivery tracking

1. **Enqueue (in the business transaction):** services append outbox intents (`eventType`, channel, recipient identity, template key, locale, minimal params = reference/link data, idempotency key = hash(unique domainEventId generated for that committed occurrence + recipient + channel/template), so retrying one occurrence is deduplicated while a later legitimate repeat event for the same entity (for example another reschedule) remains a separate notification). If the transaction rolls back, no intent exists; if it commits, delivery is guaranteed to be attempted. **A submitted request can therefore never be lost because WhatsApp/email is down.**
2. **Dispatch:** a worker (mechanism `TBD-TECH-06`: scheduled job/queue compatible with the hosting) claims `queued` rows in batches, calls `NotificationSenderPort`, records `providerMessageId` → `sent`.
3. **Delivery events:** provider webhooks (§3.9) advance `sent → delivered → read` or set `failed` with a sanitized provider error code. Unknown/duplicate events are ignored safely.
4. **Retry policy (proposal, PO-amendable):** exponential backoff (e.g. 1m/5m/30m/2h), max attempts `TBD-TECH-06`, then `dead` + staff-visible task in the notifications module; manual `retry` endpoint re-queues. Non-retryable errors (invalid number, template rejected) go straight to `dead` with reason.
5. **Template governance:** template keys map 1:1 to Meta-approved templates (Utility-first set proposed in the requirements doc §4.6); template text/approval is a PO + Meta process, versioned alongside `eventType` catalog. Sending outside the 24-hour customer-service window uses templates only; free-form replies are out of scope for this API.

## Appendix A — Inherited validation rules (verified from `src/lib/validation.ts` at baseline)

Server-side validation MUST implement at least these semantics (field-error keys already localized in the dictionaries):
- **V-NAME**: required; ≥3 chars after trim. **V-PHONE**: required; Arabic-Indic/Persian digits folded, `[\s()-]` stripped, then `^\+?\d{8,15}$`. **V-EMAIL**: optional; if present `^[^\s@]+@[^\s@]+\.[^\s@]{2,}$`. **V-EMAIL-REQ**: same pattern, required.
- **V-AREA**: optional; if present must parse (Arabic digits + comma decimal accepted) to a finite number > 0. **V-DESC**: required; ≥20 chars. **V-MSG**: required; ≥10 chars. **V-ISSUE**: title ≥3 chars; detail ≥10 chars.
- **Consent**: contact consent must be `true` (current forms enforce this; WhatsApp consent is captured separately per §2.1 and its requiredness follows `TBD-PO-01` copy — a request must never be rejected solely for declining WhatsApp if PO so decides; flagged, not assumed).
- **V-ASSIGNEE**: a request entering or remaining in `inspection_scheduled`/`inspection_done` requires a non-null assignee (existing admin rule, unit-tested today); in this API those states are reached only through the linked inspection operations in §4.1.
- **V-PASSWORD**: minimum policy to be set at kickoff (`TBD-TECH-01`); until then this spec only requires: non-empty, ≤256 chars (baseline login guard), never logged/echoed.
